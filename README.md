# Glazounov AI Lab — сайт-портфолио AI-проектов

**Glazounov AI Lab** — действующий сайт-портфолио, объединяющий описание AI-проектов, ссылки на исходный код и документацию, интерактивные демонстрации и встроенного AI-консультанта.

**Сайт:** https://glazounov-ai.ru/  
**Репозиторий:** https://github.com/Glazounov-AI/glazounov-ai-lab-site  
**Основной язык интерфейса:** русский  
**Технологии сайта:** PHP, HTML, CSS, JavaScript  
**Внешний AI backend:** Python / FastAPI / OpenAI / ChromaDB / SQLite, Railway

## 1. Назначение проекта

Сайт решает несколько задач:

1. **Публичное представление работ.** Каждому проекту выделена отдельная страница с задачей, подходом, технологиями, результатами и ограничениями.
2. **Демонстрация реализации.** Посетитель может перейти к GitHub, технической документации и доступным демо.
3. **AI-консультация.** Встроенный чат отвечает на вопросы о проектах и направлениях работы с использованием отдельной базы знаний.
4. **Единая точка входа.** Главная страница, каталог проектов и контакты объединены общей навигацией и визуальным стилем.
5. **Управляемая публикация.** Изменения фиксируются в Git, а сайт развёртывается через GitHub Actions и SSH/rsync.

На сайте отображаются текущие статусы проектов — действующий backend, стабильный релиз, протестированный прототип либо завершённый эксперимент.

## 2. Реализованные возможности

- Главная страница с позиционированием, избранными проектами, информацией об авторе и контактами.
- Каталог `/portfolio/` и отдельные страницы проектов.
- Общие PHP-компоненты для шапки, подвала и конфигурации ссылок.
- Единый набор CSS-стилей и адаптивные элементы интерфейса.
- Всплывающий AI-чат на страницах сайта с темами **«Проекты»** и **«Обо мне»**.
- Серверный PHP-прокси к внешнему RAG API, без передачи backend API-ключа в JavaScript.
- Ограничение запросов и обработка ошибок на уровне PHP-прокси.
- Демо Client Request Normalizer со сравнением заранее сохранённых результатов Baseline и LoRA.
- Автоматизированный deployment из `main` через GitHub Actions на PHP-хостинг.
- Регламент подготовки и публикации демонстраций в `docs/DEMO_DEPLOY_GUIDE.md`.

## 4. Структура страниц и портфолио

### Главная страница

`index.php` содержит презентационный блок, избранные проекты, информацию об авторе и раздел контактов. Контент выводится с использованием общих `includes/header.php` и `includes/footer.php`.

### Каталог проектов

`portfolio/index.php` собирает карточки работ с описаниями, технологическими тегами, статусами и ссылками на подробные страницы.

### Страницы проектов

Каждый проект оформлен как отдельный кейс, а не просто ссылка на репозиторий. В зависимости от проекта показываются постановка задачи, рабочий процесс, архитектура, возможности, результаты проверок, ограничения и материалы.

В репозитории представлены, в частности:

| Проект | Что показывает |
|---|---|
| [RAG Assistant](https://glazounov-ai.ru/portfolio/rag-assistant/) | RAG backend, FastAPI, ChromaDB, кеширование, Railway |
| [AI IT Service Desk](https://glazounov-ai.ru/portfolio/ai-it-service-desk/) | AI-ассистент первой линии поддержки, Knowledge Base, маршрутизация |
| [AI Interview Coach](https://glazounov-ai.ru/portfolio/interview-assistant/) | Подготовка к интервью, сценарии, промпты и метод STAR |

**Принцип публикации:** описание и статус проекта должны соответствовать фактическим артефактам, тестам и доступным демонстрациям. Наличие страницы на сайте не означает, что каждый проект имеет живой backend.

## 5. AI-консультант: веб-интерфейс и backend

### Интерфейс

Виджет определяется в `includes/chat-widget.php`, подключается из `includes/footer.php`, использует `assets/css/chat.css` и `assets/js/chat.js`.

Поддерживаются:

- открытие и закрытие панели, в том числе клавишей Escape;
- переключение тем `projects` и `about`;
- отправка вопроса без перезагрузки страницы;
- отображение пользовательского сообщения, состояния ожидания, ответа и ошибок;
- блокировка повторной отправки, пока предыдущий запрос обрабатывается.

Браузер отправляет запрос **на собственный сайт**, а не напрямую на Railway:

```http
POST /api/chat.php
Content-Type: application/json
```

```json
{
  "query": "Какие проекты представлены в портфолио?",
  "topic": "projects"
}
```

### Серверный PHP-прокси

`api/chat.php` проверяет HTTP-метод, тип содержимого, размер тела, JSON-структуру, тему и длину вопроса. Затем применяет локальный rate limiter и вызывает внешний RAG API через cURL.

При передаче в backend используется:

```json
{
  "query": "Какие проекты представлены в портфолио?",
  "mode": "portfolio"
}
```

**Важная особенность:** обе темы интерфейса — `projects` и `about` — сейчас передаются в **один режим backend `portfolio`**. Переключатель меняет подсказку и оформление в браузере, но не выбирает отдельную коллекцию знаний на стороне Railway.

Успешный ответ прокси содержит только:

```json
{
  "answer": "Текст ответа AI-консультанта"
}
```

Поля `from_cache` и `model`, возвращаемые RAG backend, в ответ браузеру не передаются.

### Ограничения и обработка ошибок

В PHP реализованы следующие проверки:

| Условие | Ответ прокси |
|---|---|
| Метод не `POST` | `405` |
| Не `application/json` | `415` |
| Тело более 16 384 байт | `413` |
| Некорректный JSON, поля или тема | `400` |
| Недопустимая длина вопроса | `400` |
| Превышен лимит | `429` |
| Недоступная конфигурация | `503` |
| Ошибка сети или backend | `502` |

Таймаут соединения cURL — 5 секунд; общий таймаут берётся из серверной конфигурации. Автоматическое следование перенаправлениям отключено.

### Лимитирование запросов

`api/rate-limit.php` реализует файловый счётчик `counters.json` с эксклюзивной блокировкой `flock()` и скользящим окном 60 секунд:

- не более **5 запросов за 60 секунд с одного IP**;
- не более **30 запросов за 60 секунд суммарно**.

IP преобразуется в SHA-256 для ключа счётчика. Если файл недоступен или повреждён, функция возвращает отказ в обслуживании, а не разрешает запрос без проверки. На backend также действует собственный SQLite rate limiter; это два разных уровня ограничения.

Лимиты относятся к реализации PHP-прокси, а не к гарантированной пропускной способности внешнего API.

## 6. Безопасность и конфигурация

### Конфигурация сайта

`includes/config.php` содержит общие публичные параметры:

- название сайта;
- адрес сайта;
- ссылки на Telegram и GitHub.

Серверная конфигурация AI-прокси подключается отдельно через `api/config.php` и предоставляет:

| Ключ | Назначение |
|---|---|
| `rag_api_url` | Адрес внешнего RAG endpoint |
| `rag_api_key` | Секрет для заголовка `X-API-Key` при использовании |
| `max_query_length` | Максимальная длина вопроса |
| `rate_limit_dir` | Каталог для файлового счётчика |
| `timeout_seconds` | Общий таймаут HTTP-запроса к backend |

### Меры защиты, присутствующие в коде

- запросы к RAG backend выполняются серверным PHP-кодом;
- необязательный backend API-ключ не передаётся в браузер;
- PHP-прокси проверяет структуру и размер входных данных;
- ответы ошибок внешнего сервиса заменяются контролируемыми сообщениями;
- вывод текста сообщений в JavaScript выполняется через `textContent`, а не через вставку HTML;
- для внешних ссылок используются `rel="noopener noreferrer"` в проверенных шаблонах.

## 7. Интерактивные демонстрации

### Client Request Normalizer: Baseline vs LoRA

Демонстрация находится в:

```text
portfolio/client-request-normalizer/demo/
```

Она показывает заранее рассчитанные результаты эксперимента по адаптации Qwen2.5-0.5B с LoRA:

- выбор одного из 15 тестовых примеров;
- исходный запрос и эталонные поля;
- ответы Baseline и LoRA;
- сравнение семи полей;
- признаки валидности JSON, соответствия схеме и полного совпадения;
- сводные метрики эксперимента.

`demo.js` загружает локальный `demo_data.json` и строит интерфейс в браузере. **Модель во время просмотра демо не запускается**, API-ключ не требуется и расходы на инференс не возникают.

| Метрика | Baseline | LoRA |
|---|---:|---:|
| JSON Validity | 93,3% | 100% |
| Schema Validity | 66,7% | 73,3% |
| Intent Accuracy | 53,3% | 93,3% |
| Field Accuracy | 39,1% | 85,7% |
| Exact Match | 0% | 46,7% |

Результаты относятся к 15 синтетическим тестовым примерам. Сведения об эксперименте и форматах демо приведены в `docs/DEMO_DEPLOY_GUIDE.md`.

### RAG Assistant: API-демо

Страница RAG Assistant ссылается на [Swagger UI развёрнутого API](https://ragassistant-production-6923.up.railway.app/docs). Это **техническая демонстрация HTTP API**, а не отдельный пользовательский чат.

## 8. Развёртывание и CI/CD

### Инфраструктура

| Компонент | Платформа |
|---|---|
| Публичный сайт | PHP-хостинг Majordomo |
| Исходный код | GitHub |
| Публикация сайта | GitHub Actions + SSH + rsync |
| AI backend | Railway |
| Данные RAG | Railway Volume |

### Workflow публикации

Файл `.github/workflows/deploy.yml` определяет workflow **Deploy website to Majordomo**.

Запуск:

- автоматически при `push` в `main`;
- вручную через `workflow_dispatch`.

Последовательность:

1. `actions/checkout@v4` загружает исходники.
2. SSH-ключ и known-hosts настраиваются из GitHub Secrets/Variables.
3. `rsync -avz --itemize-changes` передаёт файлы в каталог сайта.
4. При ошибке подключения предусмотрено до пяти попыток с паузой 10 секунд.
5. Ошибка после пятой попытки завершает job с ненулевым кодом.

`rsync` в текущем workflow не использует `--delete`: удаление файла из Git само по себе не гарантирует удаление его копии на хостинге.

### Настройки GitHub Actions

Для SSH-публикации workflow получает параметры подключения к хостингу Majordomo из настроек GitHub Actions (Secrets и Variables):

| Имя | Тип | Назначение |
|---|---|---|
| `MAJORDOMO_SSH_KEY` | Secret | Приватный SSH-ключ |
| `MAJORDOMO_KNOWN_HOST` | Variable | Проверенный ключ SSH-хоста |
| `MAJORDOMO_HOST` | Variable | Адрес SSH-хоста |
| `MAJORDOMO_PORT` | Variable | Порт SSH |
| `MAJORDOMO_USER` | Variable | Пользователь SSH |


### Регламент публикации демо

`docs/DEMO_DEPLOY_GUIDE.md` определяет повторяемую процедуру: инвентаризация, выбор формата демо, подготовка, проверка, публикация, контроль ссылок, фиксация версии и откат. В нём отдельно различаются живой интерфейс, заранее сохранённые результаты, API-демо и видеозапись.

## 10. Особенности реализации

В текущей архитектуре предусмотрено разделение между публикацией контента, интерактивными демонстрациями и AI-обработкой запросов:

- **Страницы портфолио** формируются PHP-шаблонами и используют общие компоненты интерфейса.
- **AI-консультант** работает через серверный PHP-прокси и отдельный RAG backend на Railway; логика генерации ответов не размещается на PHP-хостинге.
- **Темы чата** «Проекты» и «Обо мне» организуют взаимодействие в интерфейсе. Оба типа запросов передаются в режим `portfolio`, который использует общую профильную базу знаний.
- **Ограничение нагрузки** реализовано на двух уровнях: файловый счётчик PHP-прокси и отдельные механизмы RAG API.
- **Демо Client Request Normalizer** воспроизводит сохранённые результаты эксперимента и не требует запуска модели на сервере.
- **Публикация сайта** выполняется через GitHub Actions и `rsync`; обновление backend на Railway управляется отдельно.

Эти решения позволяют независимо развивать сайт, демонстрации и AI-сервис, сохраняя единый пользовательский интерфейс.
